# Browser harness patterns for MORPHIC

Research snapshot: 2026-10-16. The Zcode and Grok Build findings below come from local source checkouts at the pinned commits listed here. `agent-browser` was not present as a local checkout; its upstream `main` SHA was resolved and its README and reference docs were read at that revision. MORPHIC observations describe the checked-out working-tree contents; the repository HEAD was `65dc83953940908c866e327b8bf848ddd235009d`, and some compared Core files already had local edits. No model inference or live-site run was performed.

## Findings

The useful common pattern is a small deterministic harness around each model decision: identify the exact browser session and tab, show a compact fresh observation, perform a bounded action, return a structured result tied to that action, and verify the expected page effect before the next decision. Zcode is strongest on browser targeting and observation discipline; Grok Build is strongest on tool lifecycle, recovery, memory checkpoints, and stale-write handling; `agent-browser` has the clearest concrete browser/session primitives. These are patterns to adapt, not drop-in replacements for MORPHIC's embedded Electron view.

The key MORPHIC failure modes are concrete. Browser ids are small integers reissued from 1 on every snapshot, with no snapshot revision attached to an action. A reply may batch six actions against the same initial snapshot. The browser host returns `ok: true` when DOM dispatch succeeded, not when the intended application state changed. The model can mark a task done in that same reply, and the step limit also ends with status `done`, even though no success condition is checked. These can turn a harmless DOM-level success into a false report of task completion.

## What the harnesses actually do

| Concern | Zcode | Grok Build | `agent-browser` |
|---|---|---|---|
| Browser implementation | Browser-use plugin wraps supported IAB, extension, or CDP backends and exposes only their effective capabilities. Each JavaScript tool call starts a fresh JS kernel, while browser tabs live for the Zcode process. | No first-party interactive browser driver in the checked-out tool registry. The `browser_use()` agent preset is prompt guidance to use available browsing tools; the only `browser_tab`/`browser_network_details` test is a comment-only ignored scaffold. Browser access must come from an external tool/MCP. | CLI communicates with a browser daemon; `--session` gives each named session separate cookies, storage, cache, history, and tabs. A session is ephemeral unless restore is requested. |
| Tool/turn results | Streamed calls retain provider call IDs; results and errors are matched back to those IDs, persisted in the turn, and fed into the next model turn. Execution emits batch lifecycle events. | Native tool calls have IDs and paired results; the actor executes batches and continues the model loop until it has a final response. Rejections still produce a failed result for each call so the batch remains paired. | CLI commands return structured JSON envelopes such as success/data, with snapshots carrying both text and refs. It is a command harness, not itself an LLM turn manager. |
| Target selection | Model-visible `tabs.list()` before a logical operation, then bind by stable tab ID or verified URL/title in the next call. Never select by array position; user tabs are observed separately and explicitly claimed. | Not applicable to an inbuilt browser. | Tab IDs are stable `t1`, `t2`, etc., not array positions. `--pin-tab` makes a missing tab a strict `tab_gone` error with recovery metadata instead of silently selecting another. |
| DOM refs | Ground locators in the latest compact accessibility snapshot; ambiguity, timeout, or a missing match requires a new snapshot and rebuilt locator. | Not applicable to an inbuilt browser. Hashline coding edits use read-derived anchors, validate the original snapshot, and return fresh anchors/context on stale or ambiguous edits. | Snapshot refs (`@eN`) persist for surviving DOM nodes across same-document changes, are invalidated by replacement/navigation, and are never recycled within the session. Virtual accessibility nodes are snapshot-local. |
| Verify/recover | After an action, inspect the expected page/tab effect. Never replay a timed-out locator unchanged; re-snapshot and reconstruct. Routine waits are capped at three seconds; `networkidle` is unsupported. | Tool execution is traced and errors are returned in-band. The turn loop has repeated-call nudges and hard stops; hashline edits explicitly reject stale anchors rather than guessing. | Snapshot after navigation/dynamic changes; a pinned-tab failure is explicit. The CLI also exposes screenshot, console/errors, network/HAR, trace, profiler, and optional `.webm` recording for diagnosis. |
| Checkpoints/memory | Tool results and session turns are persisted. Successful file-mutation tool results can create before/after workspace checkpoints tied to the tool-call ID. Browser tabs themselves survive only the current Zcode process. | Conversation and tool call/result state are durable. Pre-compaction memory flush and compaction checkpoints write resumable history artifacts; memory freshness is surfaced. | Optional session restore persists browser state and periodically autosaves. Restore checks can keep a valid previous state when the attempted restore fails. |
| Images/video | A screenshot is an explicit capability; IAB screenshots must be emitted in the same JS call to be visible to the model. It is not implicit in the DOM snapshot. Recording may be unavailable by backend. | Screenshot bytes from an external MCP can be attached to a deferred multimodal follow-up when the harness/model supports vision. A text-only harness drops the image bytes and leaves a placeholder. The repo offers no built-in visual browser or video perception. | Can capture screenshots and record `.webm`; this makes artifacts available, not visual understanding. A model must have a supported image/video input path to perceive them. |

Grok's general coding tools are useful beyond code editing: the hashline editor only accepts anchors grounded in a prior read, validates a batch against that read snapshot, and rejects stale or ambiguous edits with fresh context. MORPHIC can apply the same contract to browser actions: action references must name the observation version that produced them, and stale references must fail closed with the new observation needed to recover.

## MORPHIC gaps in the current source

- **Provider protocol is lossy for tools.** [`model.ts`](../../src/core/model.ts#L13) exposes one string reply; the OpenRouter adapter converts native calls to textual `<<action ...>>` lines and discards provider call IDs ([lines 78–116](../../src/core/model.ts#L78)). Chat tools are parsed/applied once in [`agent.ts`](../../src/core/agent.ts#L228), with up to six requests, and there is no generic tool-result → model continuation loop. Browser automation is a separate prompt/parse loop.
- **Snapshot ids can become stale or target a replacement.** [`browser-host.ts`](../../src/main/browser-host.ts#L27) strips markers and numbers elements from 1 for each snapshot; `ACT` later queries by that numeric marker ([lines 61–97](../../src/main/browser-host.ts#L61)). The action schema carries only the number, not page/session/snapshot identity. The task loop obtains one snapshot, then can execute as many as six actions from that observation ([`browser-task.ts`](../../src/core/browser-task.ts#L13), [`agent.ts`](../../src/core/agent.ts#L407)). A stale or reused number is therefore not distinguishable from a current target.
- **Dispatch success is treated as action success.** `ACT` reports `ok: true` after a click/input/change event; `BrowserHost.act()` waits 200 ms and up to six seconds for loading, then reports only whether the URL changed ([`browser-host.ts`](../../src/main/browser-host.ts#L214)). It does not read the value back, assert a route or visible state, or detect many same-URL SPA updates. The task loop takes another observation only after explicit navigation/back, URL change, or action error ([`agent.ts`](../../src/core/agent.ts#L443)).
- **Completion has no deterministic predicate.** The prompt tells the model to set `done` when it thinks the task is finished and even tells it to set `done` when it is stuck ([`browser-task.ts`](../../src/core/browser-task.ts#L140)). Core trusts `reply.done` and saves a routine ([`agent.ts`](../../src/core/agent.ts#L459)); exhausting the 15-step budget also calls `finish('done', ...)` ([line 467](../../src/core/agent.ts#L467)). A limit pause should have a separate `paused`/`needs_input` status; only verified goal conditions should produce `completed`.
- **Long-task state is not a browser resume protocol.** MORPHIC persists task steps and user memory/routines, but the running loop has no explicit task checkpoint/reacquire procedure. Its Electron partition persists site data across launches, while the actual `WebContentsView` and current page are held in memory ([`browser-host.ts`](../../src/main/browser-host.ts#L23), [lines 112–133](../../src/main/browser-host.ts#L112)). After restart, saved cookies do not prove the former page or task context is still current.
- **Observation is heuristic and text-only.** Snapshot selection is a CSS list of up to 120 visible interactive nodes and up to 3,500 characters of page text, not a full accessibility tree ([`browser-host.ts`](../../src/main/browser-host.ts#L27)). The model prompt includes element labels and up to 2,200 characters of page text but does not clearly delimit page content as untrusted data ([`browser-task.ts`](../../src/core/browser-task.ts#L132)). MORPHIC uses `capturePage()` for a UI still while overlays cover the browser, not as model input ([`browser-host.ts`](../../src/main/browser-host.ts#L172)); current model interfaces have no image/video input. The prompt should not ask a text-only model to inspect images or video.
- **No code-editing tool surface.** The current Core tool set serves reminders, memory, planning, browser startup, and connectors; a coding harness would need separately designed, permissioned file tools and checkpoints rather than assuming the browser tools cover coding.

## Recommended adaptations

1. **Give every action an explicit envelope.** Store `taskId`, `stepId`, `callId`, `sessionId`, `tabId`, `snapshotId`, action and arguments. Return one structured result for every call ID, including errors, with the URL and concise before/after evidence. Keep textual action markers as a provider adapter if needed, but parse them into this same internal representation; preserve native IDs when available.
2. **Use a real snapshot token and non-recycled refs.** Return a compact role/name/state snapshot with stable refs and a monotonically increasing snapshot ID. Bind actions to `{tabId, snapshotId, ref}` and reject mismatches as `stale_snapshot`, together with the refreshed observation. Use browser-native accessibility/locator APIs where the embedded Electron surface permits them; retain CSS/DOM inspection only as a disclosed fallback. Limit routine steps to one state-changing action followed by one targeted observation. Batch independent field fills only if action results read values back and no intervening re-render/navigation occurs.
3. **Verify effects in code before claiming success.** Define task completion checks up front where possible (expected URL/headline, selected item, saved draft/status, visible confirmation, or read-back field values). After clicks, wait for a concrete expected state; distinguish `dispatched`, `observed`, and `verified`. If state is uncertain, report uncertainty, take another snapshot, and recover rather than claim done. Use separate `completed`, `paused`, `needs_input`, `stopped`, and `failed` statuses.
4. **Make retries action-aware.** After timeout, stale reference, or non-effect, refresh the page and re-plan; never blindly replay a click, submit, purchase, send, or other side effect. Permit short retries for idempotent reads/waits only. Detect repeated identical calls and stop with a clear recovery prompt after a small bounded count.
5. **Persist a task checkpoint, not just a transcript.** Record goal, current stage, verified facts, completed effects, approvals, last observed origin/URL, and next safe action. On resume or app restart, reacquire the intended embedded page/session, check its URL and a fresh snapshot, then continue only if the checkpoint still matches. Preserve browser storage only within the existing browser privacy controls. Do not promote a model-generated routine unless its steps reached verified completion; keep routine memory separate from personal preference memory.
6. **Label observations and protect untrusted page content.** Bound snapshot size and prioritize the active region, headings, form labels, buttons, and validation errors. Mark site text as quoted/untrusted evidence and instruct the model to follow the user's request and harness policy, not commands embedded in web content. Keep private values out of logs and model results where feasible.
7. **Expose capabilities truthfully.** Advertise structured capability flags for accessibility snapshots, screenshot input, download, upload, recording, and extra tabs. Only request visual inspection when the selected model can receive images and the host can provide them. Keep screenshots/recordings as optional diagnostic artifacts unless the model's input path is verified. For an inaccessible canvas or video, ask the person or report a concrete unsupported capability instead of guessing.
8. **Adopt lifecycle/checkpoint ideas without importing whole harnesses.** Borrow Zcode's stable tab selection, fresh-snapshot discipline, short timeout budget, and result association; borrow Grok's paired tool results, bounded repeated-call handling, explicit checkpointing, and stale-edit rejection; borrow `agent-browser`'s stable tab IDs, scoped refs, strict missing-tab behavior, and diagnostic artifacts. Avoid assuming Grok Build contains a browser, that a recorded video is understood by a model, or that a generic CLI daemon should replace the embedded Electron browser.

## Long-horizon validation design

Build deterministic local fixtures on three distinct origins, with scripted delays and seeded user data. A representative task spans: (1) search a store fixture and find a specific product/price/availability; (2) open a manufacturer or policy fixture and check a compatibility fact; (3) enter the verified product and fact into a draft request on a third fixture, leaving its final send/submit for explicit approval. The expected result is a precisely checked draft plus evidence of the source facts; no external website or real transaction is involved.

Run the same scenario over multiple model turns and an app restart: pause after the first verified fact, ask an unrelated question, then resume; separately close/relaunch the app after a checkpoint and continue with persisted browser storage but a newly observed page. Include controlled faults: the result list re-renders between snapshot and action; duplicate “Open” buttons; a same-URL SPA transition; a popup/new-tab link; slow DOM readiness; invalid form data; login requiring human input; a page containing instructions aimed at the agent; and a consequential submit. Expected behavior should be precise: stale action rejected and re-observed, correct tab retained or explicitly claimed, sensitive fields handed to the person, consequential action approved, and no task called complete before its draft/fact predicates pass.

Use a deterministic scripted model fixture first to exercise the host and all recovery branches, then repeat the same bounded task with the chosen fast model and a control model. For each run, retain redacted task/action IDs, prompts and structured tool results, snapshots, URL transitions, console/network evidence, checkpoints, latency, and screenshot artifacts only where visual diagnosis is needed. Measure verified completion and false completion separately, along with wrong-target actions, stale-ref rejection/recovery, duplicate side effects, repeated calls, extra model rounds, token/time cost, and restart recovery. The fast model should succeed through short observations and explicit state receipts; do not make it infer whether a click worked from an `ok` bit.
