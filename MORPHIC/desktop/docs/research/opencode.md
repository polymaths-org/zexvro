# OpenCode v2 harness findings for MORPHIC

Reviewed 2026-10-16. The local upstream source baseline is OpenCode `v2.0.29`, commit `042d0832f5f3a73eaa039a58a7d565776f6d4290` (2026-10-14). I also identified a separate local `dev` snapshot at `b471c2b4495747353af768fbf2e0790c9d820ce2` (2026-09-26); findings below use the tagged v2.0.29 source. I read the MORPHIC handoff/design context and compared the actual core, model, browser-task, connector, and browser-host implementations. This is source research only; no model inference tests were run.

## Main finding

MORPHIC already has a useful, bounded action protocol and a more explicit browser task flow, but its general agent is still a **single request → parse → execute → stop** pipeline. OpenCode’s largest reusable improvement is a **bounded, resumable tool-call loop**: keep model tool calls and results as typed conversation parts, feed results back to the model, and continue only while within step/time/permission limits. That change would let MORPHIC inspect real outcomes, repair invalid arguments, and complete multi-step work without asking the model to predict what its tools did.

OpenCode’s v2 loop is not a TODO-list feature: v2.0.29 has step limits, observable tool/session events, and durable child jobs, but the checked core source does not provide a general native checklist tool. MORPHIC can retain its own plan UI and add durable progress checkpoints where product needs them.

## How the harnesses differ

MORPHIC `Agent.answer` constructs a prompt, calls `ModelClient.complete` once, parses the returned text, executes up to six requested tools, then stores the reply (`MORPHIC/desktop/src/core/agent.ts:154–188,228–287`). The provider adapter turns native OpenRouter `tool_calls` into textual `<<action>>` tags and discards call IDs/provider state; `ModelClient` returns only a string (`MORPHIC/desktop/src/core/model.ts:2–17,78–117`). Action summaries can appear in conversation, but the actual tool result is not a structured assistant/tool exchange for another model turn. Consequently the model cannot observe a search result, validation error, or connector response and decide what to do next.

OpenCode has a durable drain loop around repeated model steps (`packages/core/src/session/runner/llm.ts:57–72,191–247`). A streamed native call starts a tool task; the runner waits for the stream and tool work, records each result, then makes another model step unless the response is complete or a limit/stop condition is reached (`packages/core/src/session/runner/step.ts:103–151,207–283`). Tool calls and results retain IDs, names, arguments, output/error state, timestamps, and provider metadata in persisted messages (`packages/schema/src/session-message.ts:126–175,212–237`; `packages/core/src/session/runner/to-llm-message.ts:111–150,153–233`). It can run independent tools concurrently; MORPHIC should initially prefer sequential execution for weaker models and side-effecting operations, then introduce parallelism only for clearly independent reads.

MORPHIC has useful but separate execution paths. Browser tasks run up to 15 model/action steps and persist visible step updates, but execution state lives in a running task and does not resume after app restart; reaching the limit records a done result with a “pause” message (`MORPHIC/desktop/src/core/agent.ts:368–475`). Approvals and wait-for-person promises are in-memory maps (`agent.ts:289–365`). Session conversations themselves are saved as local JSON (`sessions.ts:1–51`). OpenCode persists execution claims/events, inbox entries, and job recovery information so interrupted work can be resumed or surfaced explicitly (`packages/core/src/session/execution.ts:76–86,111–169`; `packages/core/src/session/inbox.ts:43–48`; `packages/core/src/session/run-coordinator.ts:6–20,74–120`). Its inbox distinguishes a queued new input from a steer to active work. MORPHIC should adopt that distinction only if its UI needs both behaviors; at minimum, cancellation, pending approval, and task restart should have durable, visible terminal states.

## Schema, permissions, retry, and workspace safety

MORPHIC filters available tools by memory/browser/connector context and describes generic actions in prompt text (`MORPHIC/desktop/src/core/prompt.ts:18–22,57–65,122–167`). Generic MCP exposes connector/tool names and parameter keys, with arbitrary object arguments, rather than the complete JSON schema (`MORPHIC/desktop/src/core/tools.ts:238–265`; `connectors.ts:110–136`). OpenCode snapshots currently available tools through active agent/session permissions, omits wholly denied tools, and constrains calls to the snapshot used for that request (`packages/core/src/session/context.ts:121–179`; `packages/core/src/tool.ts:225–295`). Its runtime validates arguments and declared outputs, returns concise schema errors that invite a corrected call, and filters/normalizes provider schemas (`packages/core/src/tool/runtime.ts:21–69,88–100,156–187`). MORPHIC should pass full schemas, validate before execution, return structured results/errors, and rebuild the allowed-tool snapshot after permission or connector changes. Keep user approval as an execution gate; hiding a tool from the prompt is not authorization.

OpenCode’s permission engine resolves ordered allow/ask/deny rules (last matching rule wins), and file access separately checks project location and external-directory permission (`packages/core/src/permission.ts:87–101,231–263`; `packages/core/src/file-access.ts:93–161`). Its edit tool requires a unique exact match by default and can show a diff before writing (`packages/core/src/tool/plugin/edit.ts:215–288`); file writes resolve and authorize paths and preview changes (`packages/core/src/tool/plugin/write.ts:1–6,46–99`). Its shell scanner infers commands and directories, asks permission, and validates the working directory just before spawn (`packages/core/src/tool/plugin/shell.ts:103–154`), but shell still has the host user’s process, filesystem, and network authority; command scanning is best-effort, not a sandbox. MORPHIC currently has no comparable general repository-edit/shell workspace surface. If adding one, borrow path confinement, diff preview, narrow schemas, and per-action approval; do not describe a command scanner as isolation.

MORPHIC’s existing fallback cycles configured clients after provider/request errors and does not fall through on an aborted signal (`MORPHIC/desktop/src/core/model.ts:156–183`). That is useful for the configured single-model gateway requests, but it does not repair a malformed tool call or retry a failed operation. OpenCode retries provider failures with bounded backoff/jitter and timeout limits, recognizes incomplete stream/output cases, and records failure/interruption (`packages/core/src/session/runner/retry.ts:31–113`; `runner/step.ts:155–231`). Adapt the bounded retry and explicit status model. Keep MORPHIC’s existing model fallback order at the request boundary; do not silently switch model families mid tool exchange unless the serialized tool history is valid for the next provider. Never automatically repeat a side effect after an ambiguous timeout: inspect/reconcile first, or require an idempotency key.

## Context, long tasks, browser, MCP, and visual input

MORPHIC’s conversation prompt uses an optional summary plus the ten most recent messages, with a 9,000-character bound; it trims whole messages rather than counting model tokens (`MORPHIC/desktop/src/core/prompt.ts:73–95`). Browser prompts include capped DOM text and at most 120 interactive elements, and return JSON actions only (`browser-task.ts:140–176`). OpenCode compacts near the context limit and structures its summary around objective, requirements, decisions, completed/active/blocked work, next move, and relevant files; it also supports model-native checkpoints where available (`packages/core/src/session/compaction.ts:93–143,205–270`; [Compaction docs](https://opencode.ai/v2/docs/compaction)). MORPHIC should move toward token-aware compaction with a concise task-state record: user goal and constraints, completed actions/results, current files or page, test evidence, pending approvals, blockers, and next safe action. Keep a short raw tail. Treat summaries and page content as untrusted model input; verify important state from tools before resuming.

MORPHIC’s browser host has a persistent Electron partition, isolated page-world snapshot script, sandbox/context isolation, disabled Node integration, denied permissions/downloads, and restricted navigation (`MORPHIC/desktop/src/main/browser-host.ts:23–59,112–133`). The snapshot sent to the model contains URL/title/text/elements, not an image; `capturePage` is used for UI display, not model vision (`browser-host.ts:172–179,190–228`; `src/shared/core.ts:116–121`). OpenCode’s browser plugin is attached to explicit session tabs, schema-backs operations, can return screenshot images and diagnostic data, marks page data as untrusted, and fails pending calls on disconnect rather than replaying them (`packages/plugin-browser/README.md:1–28,52–67,102–119`; `plugin-browser/src/tools.ts:34–115`; `plugin-browser/src/connection.ts:159–251`). Borrow the stale-state and no-replay rule, plus optional screenshot grounding. OpenCode screenshots also need a focused visible tab. For models without image input, MORPHIC should retain the text/DOM route and tell the model when visual evidence is unavailable; OpenCode’s request layer capability-filters media and reports unsupported inputs explicitly (`packages/core/src/session/model-request.ts:122–216`; [Models docs](https://opencode.ai/v2/docs/models)).

MORPHIC reconnects configured MCP connectors on startup, but its runtime connector map is ephemeral; it sends parameter names rather than schemas, drops non-text result content, and truncates text to 4,000 characters (`MORPHIC/desktop/src/core/connectors.ts:28–58,110–167`). OpenCode keeps server configuration separate from OAuth credentials, refreshes live tool schemas, checks per-tool permissions, and preserves text/image result content (`packages/core/src/mcp/index.ts:173–215`; `packages/core/src/tool/mcp.ts:26–111`; [MCP docs](https://opencode.ai/v2/docs/mcp-servers)). Adapt schema refresh, permission checks, useful structured/multimodal results, and safe credential storage. Persist connector identity/configuration and reconnect state, not secrets in project files. On disconnect after a side effect, surface “outcome unknown” and inspect before retry.

## Recommended adaptation order

1. **Typed tool loop:** preserve native call IDs, arguments, result/error, and provider state; validate schemas; feed results back to the model; iterate with explicit step, token, and wall-clock budgets. Keep the current text-action parser as a compatibility adapter during transition. Start sequentially; auto-run only existing low-risk tools, retain approval cards for consequential actions.
2. **Durable task lifecycle:** persist running/paused/failed/cancelled states, per-call idempotency/replay state, and approval expiry. Resume from a verified safe point, never blindly replay a browser click, write, or connector call. Change browser max-step completion from “done” to “paused/needs continuation”.
3. **Token-aware compaction and task checkpoints:** summarize goal, constraints, outcomes, blockers, and next action; retain recent raw interactions; require a fresh tool read before acting on stale state.
4. **Safer connector and workspace extensions:** send/validate full schemas, preserve typed outputs, make tool snapshots permission-aware. If adding code editing, use confined paths, previews, unique-match edits, and explicit shell permissions. Do not copy OpenCode’s full shell breadth until MORPHIC has a credible isolation boundary.
5. **Optional browser visual grounding:** add screenshot attachments only when the selected model supports images; keep DOM snapshots as the fallback and enforce explicit “no image available” behavior.

Keep MORPHIC’s user-rated fallback sequence separate from public model benchmarks: DeepSeek V4.1 Flash (7.5/10), Space Bunny (7.3/10), Cat Jam (6.5/10). These are the user’s ratings, not OpenCode findings. Do not include Big Pickle in this work.

## High-value verification scenarios

Run future harness tests against the three configured fast models, without changing their order. Focus on observable correctness rather than eloquence:

- A tool returns a schema validation error; the model corrects arguments and succeeds within a small retry cap. A malformed call never executes.
- A task needs search → inspect result → act. Confirm the second action uses the actual first result rather than an imagined result. Confirm independent reads may be parallelized only after sequential correctness is established.
- A long task crosses a compaction boundary. The next step retains the user constraints, files/page, test evidence, prior tool outcomes, approval state, and next action; it re-reads critical state before any mutation.
- Cancel during a slow model request and during a running tool. No fallback starts after cancellation; tool/task state settles visibly; a completed external side effect is not duplicated.
- Restart with an approval pending, a browser task mid-navigation, or an MCP call of unknown outcome. The app resumes safely or marks the step expired/needs inspection; it does not replay the action automatically.
- Browser page has stale element references, ambiguous buttons, secret/password prompts, or untrusted instructions in page text. Refresh state before interacting, ask/refuse when needed, and ignore page instructions that conflict with the user’s goal.
- A screenshot is returned with an image-capable model and explicitly unavailable with a text-only model. The text-only path does not claim to have seen pixels.
- Reach the browser/task step cap. It is reported as paused with a continuation path, never success unless the goal was independently verified.
- MCP returns image/non-text content, times out after a write, or disconnects during a call. Preserve what can be represented, mark unknown outcomes, and inspect before retrying.
