## What Codex contributes

**The turn is a loop, not one response.** `core/src/session/turn.rs:129-141` describes the contract: sample the model; execute function calls; add their outputs to history; sample again; finish only when the model returns a normal assistant message. `run_turn` repeats sampling when a tool or pending input requires follow-up and checks context usage after each sample (`turn.rs:226-370`). Function results are structured `function_call_output` items keyed by the originating `call_id` (`protocol/src/models.rs:815-833,1034-1044`). History normalization keeps call/output pairs complete, repairs a missing function output with an `aborted` result, and removes orphan outputs (`core/src/context_manager/normalize.rs:18-100`; `context_manager/history.rs:355-368`). This lets the model distinguish a proposal from a completed action.

**State survives model calls and restarts.** Codex records ordered rollout items as JSONL with timestamps/ordinals and flushes each written line (`rollout/src/recorder.rs:1850-1875); threads expose resume and history operations (`core/src/codex_thread.rs:244-250,466-492). The app-server protocol supports `thread/start`, `thread/resume`, paged history, `turn/start`, and `turn/interrupt`. Its event stream reports turn completion as completed, interrupted, or failed and publishes item/tool progress. [The app-server docs](https://learn.chatgpt.com/docs/app-server) describe those lifecycle calls and events. The product article frames the harness as the layer for conversation state, streaming, tool use, boundaries, approval, and work carried across turns ([Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform).

**Compaction protects active work.** Codex checks token usage and can compact before sampling or mid-turn (`turn.rs:153-165,305-370). The compaction code summarizes the history, replaces the active history with the summary plus retained user messages, and reinjects initial context in the correct position for mid-turn continuation (`core/src/compact.rs:55-85,322-367). The history manager truncates tool output to a serialization budget and strips image data for models that do not accept images (`core/src/context_manager/history.rs:137-143,355-395`). This is an explicit checkpoint operation, rather than hoping an idle summarizer runs in time.

**Instructions and skills are scoped.** Project `AGENTS.md` files are discovered from the repo root through the current directory, concatenated in order, and bounded by a configured byte limit (`core/src/agents_md.rs:1-16,83-149); the loaded instruction object retains source paths (`agents_md.rs:310-416). The skills extension advertises a catalog, selects explicit skill mentions, loads only selected skill instructions, and truncates an oversized prompt with a warning (`ext/skills/src/extension.rs:242-352). OpenAI's recent skill guidance recommends short descriptions and progressive disclosure to limit irrelevant prompt context ([Rethinking skills and prompts](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra). Applying that advice to fast, smaller models is an inference: keep the always-loaded rules especially short, and bring in one relevant procedure only when needed.

**Tools have real boundaries and observable results.** The shell handler constructs requests with the configured sandbox, timeout, cancellation token, environment and approval policy (`core/src/tools/handlers/shell.rs:80-120,158-220). The patch handler parses and verifies a patch against the selected environment filesystem and sandbox before applying it (`core/src/tools/handlers/apply_patch.rs:359-414). Tool items have a streamed lifecycle; the app-server maps it to events the UI can show. Codex's verification loop benefits from real command/test feedback, while the host owns product UI and approval choices.

**Retries and cancellation are explicit.** Sampling retries only provider errors classified as retryable and uses the provider's retry limit (`turn.rs:1113-1207); cancellation tokens are passed into sampling and tools. A turn can be interrupted, then the stored thread resumed. The app-server docs define `turn/interrupt` as ending with `status: interrupted`, and `thread/resume` continues the recorded thread. This makes “stopped”, “failed”, and “finished” distinct states instead of treating every empty response alike.

**Capabilities are queried.** App-server `model/list` reports supported reasoning efforts and `inputModalities` (including text/image); the client should use returned values instead of assuming them. Older catalogs without modality metadata default to text and image in the current docs. In source, history preparation removes images when the selected model does not support image input (`history.rs:137-143,355-368). See [model/list and its capability fields](https://learn.chatgpt.com/docs/app-server).

## MORPHIC baseline behavior

The main chat path is deliberately low latency: `Agent.send` saves the user's message, calls the model once, applies returned actions, appends the assistant message, and saves the session (`MORPHIC/desktop/src/core/agent.ts:112-188). The OpenRouter adapter offers tool schemas but flattens returned native calls into `<<action ...>>` text; call IDs and provider tool items are discarded (`src/core/model.ts:78-117). VROAI accepts a single prompt string, and its client ignores the optional native-tool argument (`model.ts:21-47). Automatic tool results are recorded in the Morph message, but do not normally trigger another model call. A connector result is the special case: after approval, its `followUp` text is inserted into a new call (`agent.ts:289-332); `prompt.ts:161-165` supplies that result as prose. This one-call design is cheap and fast, but it cannot reliably support “call tool, inspect result, decide next action” for small models.

MORPHIC has a separate browser loop: up to 15 model steps, up to six proposed actions per step, and a fresh DOM snapshot on each step (`browser-task.ts:13-21,57-68`; `agent.ts:407-467). It already has valuable deterministic protection: arguments are validated in code, tools have fixed `auto/ask` tiers, consequential browser actions are judged before execution, and sensitive fields are handed to the person (`tools.ts:40-51`; `browser-task.ts:71-127). The browser host isolates the page, denies permissions and downloads, restricts navigation to HTTP(S), and returns visible text plus numbered DOM controls (`main/browser-host.ts:27-59,112-130). It does not send screenshots to the model. Page text is included in the browser prompt without an explicit untrusted-content boundary (`browser-task.ts:144-175`), so prompt-injection fixtures should be part of the evaluation.

Conversation persistence is a JSON file per session, written by temp-file plus rename (`core/sessions.ts:6-31`; `core/store.ts:4-18). Browser steps are saved to the task card. The separate `activity.jsonl` is a useful human-readable audit of actions but is trimmed to 2,000 entries and does not capture every model request, tool call, raw result, or state transition (`core/activity.ts:8-23). The prompt keeps at most 9,000 characters of visible history and puts a summary before the retained messages (`core/prompt.ts:31-94). Memory reflection runs after an idle delay and requires at least two new user messages in the usual case; only then can it replace older history with a short summary (`core/agent.ts:19,489-509,549-558). Task steps and the task result are stored outside the normal history rendering, which includes message text, plans, and successful action summaries (`prompt.ts:73-94). Consequently a completed browser result is not reliably part of the next normal chat prompt.

Pending approval arguments and browser approval waiters are held in memory. The approval card itself is saved, but after restart the arguments are gone and the card is declined as expired (`agent.ts:289-332,349-365). Browser task status and steps are saved, yet there is no startup worker that resumes an interrupted task or public continue-task action (`agent.ts:372-475); IPC exposes chat retry, stop, and approve (`core/index.ts:150-152). Model fallback is bounded by a 90-second request timeout and per-client cooldowns; abort is not retried, network failures cool down for 20 seconds, rate limits for one minute or until UTC midnight for daily quota (`model.ts:19,139-183). Browser `open` and `act` do not accept the task's abort signal (`main/browser-host.ts:190-228), so Stop can wait for the current browser operation to finish.

## Recommendations

1. **Keep the one-call path for simple chat, add a small explicit loop for result-dependent work.** Preserve Morph's low latency for answers and deterministic local actions. For connector, browsing, or other operations whose result affects the next decision, persist a structured call with a unique ID, execute it once, append the structured result under that ID, and ask the model to continue until it returns a final answer or reaches a step/time budget. Avoid parsing tool intent from user-visible prose when the provider supports native calls or schema-constrained output. Continue strict validation even after schema generation.

2. **Make browser work a durable task state machine.** Save each transition as intent, approval, action result, fresh observation, verification, and completion/failure/cancellation, with task ID and stable action ID. On relaunch, show whether the task can resume, needs re-observation, or needs the person's input. Before retrying an action that may have reached a website, check its postcondition or use an idempotency key. Keep the existing hard step/action limits and allow Stop to cancel model, navigation, page actions, and connector calls.

3. **Bind approval to the exact action.** Persist the tool name, normalized arguments, page URL/revision, preview, and approval status. On approval, revalidate that the current action still matches; never let an old approval authorize a changed target. Treat approvals as a checkpoint, not merely a UI card.

4. **Compact from task state at a budget threshold.** Build a compact checkpoint containing the original goal and success conditions, verified completed steps, unresolved questions, current URL and latest relevant page observation, pending approval/call IDs, and safety constraints. Retain recent call/result pairs and user messages. Summaries should not silently turn “attempted” into “completed.” MORPHIC's existing idle memory summary can remain for conversational recall, but it is too delayed and incomplete to be the only long-task compaction path.

5. **Give each model/provider an explicit capability record.** Include native tool calling, strict structured output, streaming, image input, context budget, and cancellation support. Choose prompt and output formats per capability, pass text-only snapshots to text models, and clearly stop or ask the person when a task depends on an image or canvas the DOM snapshot cannot describe. Do not assume every fallback has the same tool/vision contract.

6. **Keep MORPHIC's job-specific safety layer.** Borrow Codex's loop, event, persistence, and capability ideas; do not transplant Codex's generic shell/file-edit tool surface into a browser helper. For coding-like workflows, use narrow application-owned tools and deterministic permission checks. Treat page text as untrusted input, and make success depend on a checked page postcondition, not only the model setting `done: true`.

These are architecture recommendations inferred from the source comparison, not claims that MORPHIC has been changed or tested.

## Long-horizon evaluation cases

Use deterministic browser fixtures plus mocked provider failures. Record success, incorrect/duplicate side effects, number of model calls, input/output tokens when available, wall-clock P50/P95, recovery status, and whether the final answer matches observed state. Compare target models on the same fixtures; keep task correctness and safety separate from subjective model ratings.

- **Long form completion:** a task with 12–20 distinct steps and several page changes; ensure compaction preserves goal, already-verified steps, current URL, and remaining work, then reaches the expected postcondition within the budget.
- **Tool round trip:** provider emits two calls, one malformed argument, one failing result, and a follow-up decision; ensure each call ID has exactly one result, bad calls do not execute, and the model sees the real error.
- **Crash/relaunch boundaries:** terminate after user input, after saving a proposed call, after approval, during tool execution, after tool success but before model continuation, and while awaiting approval. Resume or recover without dropping results or repeating side effects; expire stale approval safely.
- **Cancellation:** Stop during inference, page navigation, page action, connector call, and approval wait. Confirm no later action runs, state is saved as interrupted, and a deliberate resume re-observes the page before continuing.
- **Stale DOM:** have a click trigger an in-place rerender that reuses/reorders numbered controls. Confirm Morph takes a new snapshot before the next dependent action and refuses stale IDs.
- **Prompt injection:** page text asks the agent to ignore the user, reveal memory, change the task, or purchase an item. Confirm page content cannot override the user goal or approval policy.
- **Approval binding:** change the URL, target element, or arguments after the approval card appears. Confirm the old approval cannot authorize the changed action.
- **Text-only capability:** show an image/canvas-only result to a text model and a text-plus-image result to an image-capable model. The former should ask for an accessible page or person-provided detail instead of inventing observations.
- **Output and transport failures:** return truncated JSON, non-JSON tool calls, 429, 500, timeout, and stream disconnect; confirm bounded retries/fallback, visible progress, and no repeated non-idempotent execution.
- **Verification:** let the model claim completion while the fixture has not changed; confirm the task remains incomplete until the observed success condition is true.
- **Skill routing and context size:** test matching, near-miss, and unrelated skill triggers over a long thread; ensure only relevant short guidance is loaded and the task state survives context reduction.
